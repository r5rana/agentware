# agentware_lib — module router

> **"Is the code I need already here, and which module owns it?"** — answer it
> WITHOUT reading the 20k-line monolith. This is the human-facing router; the
> machine-readable source of truth is [`catalog/modules.json`](../../catalog/modules.json)
> (generated from the AST — never hand-edited).
>
> **Answer it as a command, too:** `scripts/agentware recall "<what you're changing>"`
> surfaces the indexed KB entry that points here (id `learn-agentware-lib-module-discovery`).
>
> Regenerate the manifest after any wave: `python3 tests/_manifest_gen.py --write`
> (add `--sync-fanin` to also rewrite the per-module `Fan-in:` doclines).
> `tests/gates/test_module_manifest.py` fails loudly if the manifest drifts from
> the real tree, if a file on disk has no entry, or if a file is over its cap.
>
> The manifest is TREE-WIDE as of plan task 67: `modules` is this package's rich
> per-module view, and `files` claims every Python and shell file under
> `scripts/`, the orchestrator, the test corpus and the webui source, each with
> its layer and its line cap.

## How to find the owning module (in order)

1. **Grep the manifest** for the symbol/term you're touching:
   `grep -i "<term>" catalog/modules.json` → the `anchor_symbols`, `naming_disambiguation`,
   or `planned_layout` entry names the ONE owning module.
2. **Read that module's docstring** (first ~10 lines): `Owns:` / `Does NOT own:` (with a
   pointer to the module that does) / `Layer deps:` / `Fan-in:` (blast radius).
3. **Check fan-in** (`depended_on_by` in the manifest) before changing a core symbol —
   it lists every module that imports this one, i.e. what a change ripples into.

## Layer direction (an upward import is a test FAILURE, not a style note)

`core → (nothing above)` · `knowledge → core` · `retrieval → core (+knowledge lazily)`
· `ops → core, knowledge, retrieval` · `features → any of the above` · `cli → all (leaf; nothing imports it)`

Enforced by `tests/test_module_boundaries.py` + `tests/integration/test_*.py`.
